# 乔木 App 洞察使用说明

## 1. 产品是做什么的

乔木 App 洞察是一款 App Store 用户评价研究工具。它把一个 iOS App 的评论样本抓取下来，经过清洗、去重和 AI 分析，整理成一份可以分享、复盘和继续研究的洞察页。

它目前主要服务于三类工作：

- 竞品研究：快速了解一个 App 的用户满意点、抱怨点和版本风险。
- 产品研究：从评论中寻找反复出现的需求、缺口和可验证机会。
- 证据对齐：让产品、设计、研发和运营围绕同一份评论证据讨论。

当前项目的重点是“研究工具”，机会工作台会帮助你形成研究假设和验证动作，不会自动发布产品。

## 2. 当前功能总览

### App 搜索与识别

首页搜索框支持：

- App Store 链接，例如 `https://apps.apple.com/us/app/chatgpt/id6448311069`
- App ID，例如 `6448311069`
- 应用名称，例如 `ChatGPT`

搜索时可以选择国家/地区。当前支持中国、美国、日本、英国、德国、法国、韩国、香港、台湾等 Storefront。

如果名称匹配到多个 App，系统会以 Apple 搜索结果中的第一个结果作为主结果。

### 评论抓取与数据边界

系统会从两个来源补充评论样本：

- Apple RSS：通常包含较新的评论、版本号和时间。
- App Store 页面：补充 Apple 页面展示的评论样本。

页面会展示评论样本数量、来源构成、国家/地区构成、评分分布、版本分布和数据更新时间。它不会把样本数量直接解释成 App 的全部评论总量。

### 评论质量处理

送入 AI 前会进行轻量级预处理：

- 统一空格、大小写、符号和 Emoji 表达。
- 标记过短、Emoji 过多、重复刷屏和疑似广告评论。
- 对完全重复或高度相似的评论进行聚类。
- 为每个评论簇选择代表性评论，并保留该簇的评论数量、评分、版本和用户信息。

这套处理用于减少重复噪声和 Token 消耗，但不会把清洗后的文本当成原始事实。最终页面仍保留可阅读的评论证据。

### AI 用户评价洞察

一次分析会输出：

- 摘要：当前用户口碑和最重要的结论。
- 核心痛点：用户反复抱怨的问题。
- 产品机会：可以继续研究的需求缺口。
- 正向信号：用户愿意给高分或持续使用的原因。
- 用户分层：不同用户群体的关注点。
- 版本风险：更新、性能、限制、付费策略等风险。
- 行动建议：下一步可以验证、排查或排期的动作。
- Query Angles：后续研究可以继续追问的方向。

每个洞察尽量附带代表性证据句，并带有高、中、低优先级。

### 版本与口碑诊断

详情页会用图表辅助判断：

- 不同版本的评论数量和平均评分。
- 不同版本的差评占比。
- 常见问题主题在不同版本中的分布。
- 评论情绪随时间的变化。
- 评论的评分分布和时间范围。

这些图表适合发现“某次更新后评分突然下降”或“某个问题集中出现在某一版本”等信号。

### 研究历史与变化检测

每次成功更新评论洞察后，系统会在 App 的评论历史文件中保存一份轻量统计快照，包含样本量、评分和情绪占比、版本口碑趋势，以及评论主题的数量变化。

详情页的“研究快照与变化”会比较最近两次快照，提示评分下滑、差评占比上升、新增集中主题和版本风险。第一次生成只有一份快照时不会强行下结论，下一次更新后才开始显示变化。快照只保存统计摘要，不重复保存评论正文。

### 多国家研究对比

当同一个 App 在两个或更多国家/地区生成过洞察，详情页会显示“多国家研究对比”，比较各 storefront 的样本量、评分、好评/差评占比和主要问题主题，并链接到各地区详情页。

对比会优先使用 `sourceCountry` 与当前 storefront 一致的评论；如果页面含有跨 storefront 补样本，界面会标注混合样本和本区可识别样本数。这是研究线索，不是市场份额或整体用户满意度的估计。不同地区的样本数量、语言和用户结构可能明显不同。

### App Store 榜单

首页提供 Apple Top Charts：

- 免费榜和付费榜。
- 国家/地区筛选。
- App 类别筛选，例如效率、社交、游戏、财务、教育、健康等。
- 每个榜单展示 Top 10。
- 已生成洞察的 App 可以直接打开；尚未分析的 App 可以点击“生成洞察”。

### Hacker News 产品信号

首页还会读取 Hacker News 的公开数据，展示：

- Show HN：新产品和新项目。
- Ask HN：用户问题和需求讨论。
- 热门讨论：Top Stories。
- 得分、评论数、作者和原文链接。

它目前是外部研究线索，页面负责展示信号，不会自动把 Hacker News 讨论转成确定的产品结论。

### 机会研究工作台

访问 `/opportunities` 可以查看从已生成 App 洞察中提取的候选机会。

每个机会卡片会显示：

- 机会标题和摘要。
- 来源 App 和来源评论。
- 需求分数。
- 证据数量。
- 置信度百分比。
- 置信度理由，例如评论数量、可识别用户数、版本跨度和是否能回溯原文。
- 跨 App 重复出现的数量，以及仍然存在的证据缺口。

展开“查看研究 Brief”后，可以继续查看：

- 目标用户。
- 研究切入方式。
- 下一步研究动作。
- 可回溯的代表性评论。
- 需要人工确认的问题。
- 其他 App 中的相似信号和对应详情页。
- 给研究 Agent 的下一步任务提示词。

置信度是当前的启发式指标，不是统计学意义上的市场成功概率。它适合帮助排序和发现证据缺口，不能替代用户访谈、定量调研或真实使用验证。

### 缓存与分享

每个 App 会生成稳定的洞察页路径，例如：

`/apps/us/6448311069/chatgpt`

洞察页包含更新时间，可以直接分享给团队。首页也会分页展示已生成的 App 洞察页。

默认情况下，近期缓存会复用，减少重复抓取和 LLM 调用。公开环境还会按客户端限制每天新生成的 App 数量，默认是每天 5 个不同 App。

### 兼容的管理和分析页面

项目还保留了一组较早的数据存储和分析入口，适合本地开发或已有旧数据的环境：

- `/reviews/{appId}`：分页查看评论、查看单条评论的旧版分析结果、下载 CSV。
- `/analysis/{appId}`：查看旧版聚合分析面板和图表。
- `/prompts`：创建、编辑、删除和激活分析 Prompt 模板。
- `/settings`：查看模型配置入口和管理 Prompt 模板。

这些页面仍保留旧版 Storage 兼容能力，Prompt 管理也继续使用旧入口；首页、App 详情页、历史快照和机会工作台已经共用 JSON 缓存研究链路。新使用者建议优先使用首页、App 详情页和 `/opportunities`。

## 3. 推荐使用流程

### 第一步：启动项目

```bash
npm install
cp .env.example .env.local
npm run dev
```

打开：<http://localhost:3000>

生产构建完成后，如果使用 `output: standalone`，可以这样启动：

```bash
npm run build
npm run start:standalone
```

### 第二步：配置模型

在 `.env.local` 中至少配置：

```env
QIAOMU_LLM_API_KEY=your_api_key
QIAOMU_LLM_BASE_URL=https://api.deepseek.com/v1
QIAOMU_LLM_MODEL=deepseek-v4-flash
NEXT_PUBLIC_SITE_URL=http://localhost:3000
STORAGE_TYPE=local
QIAOMU_ADMIN_TOKEN=local-admin-token
```

不要把 `.env.local` 或真实 API Key 提交到 Git。

生产环境请设置 `QIAOMU_ADMIN_TOKEN`，用于保护旧版管理和写入接口。公网的首页搜索和增量更新不需要这个 Token，但同一个 App 的公开增量更新默认至少间隔 15 分钟。

### 第三步：搜索一个 App

1. 在首页输入 App Store 链接、App ID 或名称。
2. 选择正确的国家/地区。
3. 选择评论样本量：80、160、260 或 400 条。
4. 点击搜索。

建议优先使用 App Store 链接或 App ID，因为名称搜索可能匹配到多个结果。

### 第四步：阅读洞察页

建议按以下顺序阅读：

1. 先看平均评分、差评占比、好评占比和时间范围。
2. 查看“数据来源”，判断样本来自哪些 Storefront 和抓取渠道。
3. 阅读摘要，建立整体判断。
4. 阅读核心痛点、产品机会和版本风险。
5. 查看版本诊断图，确认问题是否和具体版本相关。
6. 查看“研究快照与变化”，确认这次结论相对上次是否发生明显变化。
7. 如果已有其他地区数据，查看“多国家研究对比”。
8. 回到“评论证据”，核对 AI 结论是否有原文支持。

### 第五步：继续研究

如果某个机会值得继续调查：

1. 打开首页的“发现机会”，进入 `/opportunities`。
2. 查看机会分数和置信度。
3. 展开“查看研究 Brief”。
4. 检查代表性评论、版本范围和用户数量。
5. 记录需要补采的数据和可能的反例。
6. 再进行用户访谈、竞品对比或小规模验证。

## 4. 首页各区域怎么用

### 已生成的 App 洞察页

这里列出本地缓存中已经生成过的 App。卡片会显示国家/地区、平均评分、评论数、差评占比和更新时间。点击卡片可以回到洞察页。

### App Store Top Charts

先选择国家、类别和免费/付费榜，再：

- 点击“查看洞察”打开已存在页面。
- 点击“生成洞察”为新的 App 抓取评论并调用 AI。

### 今日产品信号

点击卡片可以跳转到 Hacker News 原文。建议把它当作“研究线索池”，再结合 App Store 评论、用户访谈或产品数据验证。

## 5. 更新洞察

在 App 详情页点击“更新洞察”：

- 会增量抓取最新评论。
- 会重新计算评分、版本和来源统计。
- 会重新进行评论质量处理和 AI 分析。
- 页面更新时间会刷新。

公开部署默认优先使用增量更新。如果需要强制完整刷新，需要在服务端允许公开强制更新后再配置对应环境变量。

## 6. API 使用

### 生成或读取洞察页

```bash
curl -X POST http://localhost:3000/api/research \
  -H 'Content-Type: application/json' \
  -d '{"query":"ChatGPT","country":"us","maxReviews":160}'
```

`query` 可以是 App 名称、App ID 或 App Store 链接。`analyze` 默认为 `true`，设置为 `false` 时只抓取和统计评论，不调用 AI。

### 更新已有洞察

```bash
curl -X POST http://localhost:3000/api/research/regenerate \
  -H 'Content-Type: application/json' \
  -d '{"appId":"6448311069","country":"us","maxReviews":400,"incremental":true}'
```

### 获取 Apple 榜单

```bash
curl "http://localhost:3000/api/top-charts?country=us&chart=free&category=productivity"
```

### 健康检查

```bash
curl http://localhost:3000/api/health
```

### 多国家研究对比

```bash
curl "http://localhost:3000/api/research/compare?appId=6448311069"
```

该接口只读取本地已经生成的同 App 缓存，不会主动抓取新的国家/地区。

### 导出报告

旧版存储分析接口提供 Markdown、HTML 和纯文本摘要格式：

```text
/api/apps/{appId}/export-report?format=markdown
/api/apps/{appId}/export-report?format=html
/api/apps/{appId}/export-report?format=summary
```

旧版 `/api/apps/{appId}/...` 兼容接口支持 `country` 查询参数，例如：

```text
/api/apps/6448311069/reviews?country=us
/api/apps/6448311069/generate-analysis?country=us
```

读取接口未提供 `country` 时会兼容返回最近更新的地区；写入接口在同一个 App 存在多个地区缓存、但请求未提供 `country` 时会返回 `409`，避免更新错地区。

## 7. 目前没有的功能

为了避免把当前能力和规划混在一起，以下功能目前还没有正式接入：

- YouTube 榜单、视频评论或频道数据。
- 自动从 Hacker News 讨论直接生成 App。
- 自动写代码、部署和发布产品。
- 统计学意义上的市场规模或成功概率预测。
- App Store 全量评论数据库。
- 多用户权限、团队协作和审核流。

当前更适合把它当作“证据优先的 App 评价研究工具”，而不是完整的自动产品工厂。

## 8. 数据和结论的边界

- Apple RSS 和 App Store 页面返回的评论受国家/地区、分页和 Apple 返回策略影响。
- 评论样本不是 App 的全部用户，也不一定代表沉默用户。
- AI 摘要和机会提炼可能犯错，必须回到原始评论核对。
- 高评论数量只代表样本中重复出现，不等同于市场规模。
- 单个评论或单个版本的问题，不应直接升级为普遍产品机会。
- 版本风险最好结合更新时间、版本分布和多条独立评论判断。

## 9. 常见问题

### 搜索不到 App

优先使用完整 App Store 链接或数字 App ID，并确认国家/地区正确。不同 Storefront 可能返回不同结果。

### 有评论但没有 AI 摘要

检查 `QIAOMU_LLM_API_KEY`、模型地址和模型名称，然后重启开发服务器。没有 AI 时，页面仍可以查看评分、版本、来源和评论证据。

### 为什么评论数和 App Store 显示的总评论数不同

当前页面展示的是可抓取和去重后的评论样本，不是 Apple 的全量评论数据库。页面会明确展示样本边界。

### 为什么机会工作台没有候选

先为至少一个 App 生成有意义的 AI 洞察，并确保其中有产品机会或核心痛点。机会工作台是从已缓存洞察中提取候选，不会单独重新抓取 App。

### 公开环境生成次数用完

默认每天每个客户端最多生成 5 个新 App。已有缓存仍可查看；新的请求会被限流或记录到队列。服务端可以通过 `APP_REVIEW_PUBLIC_DAILY_NEW_APP_LIMIT` 调整上限。

### Docker 启动后缓存不稳定

确认 `APP_REVIEW_CACHE_DIR` 指向容器内可写目录，并为缓存目录配置持久化 volume。Serverless 环境建议使用 Vercel KV、Supabase 或其他持久化存储。
